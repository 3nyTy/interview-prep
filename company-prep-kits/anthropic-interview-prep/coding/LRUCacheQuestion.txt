PROMPT 1 (DarkInterview)
------------------------------------------------------------------------------
LRU Cache (Python) - Coding - Phone, Onsite - Software Engineer

You are given an existing in-memory LRU (Least Recently Used) cache
implementation in Python. The implementation has a bug in the cache key
generation logic that needs to be fixed. The bug is related to how the cache
handles Python's variable-length arguments (*args) and keyword arguments
(**kwargs) when generating cache keys.

Your task is to:
  - Understand the existing cache implementation and its basic functionality
  - Identify the bug in the cache key generation step
  - Fix the cache key generation to properly handle *args and **kwargs

Requirements:
  - Identify the bug - why current key generation fails with *args/**kwargs
  - Generate hashable keys - convert positional + keyword args into something
    usable as a dictionary key
  - Handle argument variations - properly process both *args and **kwargs
  - Maintain cache correctness - consistent key generation for the same inputs

Notes for candidate (Python-specific):
  - How *args and **kwargs work in Python
  - What types can be used as dict keys (hashable vs non-hashable)
  - How to convert arguments into a consistent, hashable format
  - Handle keyword-argument order: func(a=1, b=2) vs func(b=2, a=1)
  - Convert unhashable types (lists, dicts) to hashable equivalents
    (tuples, frozensets)
  - Look into Python's functools module for inspiration

FOLLOW-UP: Persistent / Durable Cache
  Extend the cache to support persistent storage:
  - Survive restarts - recover all cached data after a crash/restart
  - Avoid data loss - no data lost during normal operation or crashes
  - Maintain LRU semantics - persistence must preserve the LRU eviction order
  Requirements: disk-based storage; recovery on restart; in-memory/disk
  consistency; balance write performance vs durability.
  Discussion: storage format (JSON/pickle/custom; single vs multiple files);
  write strategy (write-through vs write-back vs append-only log); recovery
  strategy (reconstruct LRU order, store metadata/timestamps); perf trade-offs
  (sync vs async writes, consistency vs performance, disk I/O overhead).

ADDITIONAL VERBAL DISCUSSION TOPICS (no code expected):
  1. Cache eviction policies besides LRU - LFU, FIFO, Random, TTL; trade-offs.
  2. Distributed cache - consistency, partitioning (consistent hashing),
     replication, network overhead (Redis/Memcached).
  3. Thread safety - global vs fine-grained vs read/write locks; lock-free;
     deadlock prevention; contention.
  4. Memory management - size limits (count/bytes/per-entry), memory
     estimation, eviction triggers, memory-pressure handling.

PROMPT 2 (1point3acres) - same question
------------------------------------------------------------------------------
In-Memory Cache: Bug-Fix + Durability. A pre-written LRU class wrapping a
generic callable is provided.

Skeleton (similar to):
    class LRU:
        def generate_key(self, *args, **kwargs):
            # provided - has a bug; must produce a hashable, order-stable key
            ...
        def call(self, func, *args, **kwargs):
            # provided - looks up generate_key(...), calls func on miss, evicts LRU
            ...

PART 1 - Bug hunt. Fix generate_key so it:
  - accepts arbitrary positional and keyword arguments
  - returns a value that is hashable and stable (same args -> same key,
    regardless of kwarg insertion order)
  Typical fix: key = (args, tuple(sorted(kwargs.items()))) after ensuring inner
  values are themselves hashable (recurse into lists/dicts or repr them).

PART 2 - Durable cache. Make the cache survive a process crash:
  - Persist every set to disk before returning from call.
  - On startup, replay the persisted log to reconstruct in-memory state.
  - Reference approach: a write-ahead log (append (key, value, timestamp) to a
    file), with optional periodic snapshotting + log truncation.
  - Discuss durability vs throughput: fsync per write vs group commit, and what
    "no data loss" actually means.

FOLLOW-UPS:
  - CPU-bound vs IO-bound classification of the system as a whole.
  - Eviction policy interaction with persistence (don't log evictions if
    recoverable from misses; do log them if you want bounded recovery state).
  - Multi-process safety - file locks, or a single writer with a queue.

NOTES / CANONICAL DURABILITY SPEC:
  Persisted state must (a) recover after a crash to the exact in-memory cache
  contents and (b) preserve LRU ordering so the next eviction matches what would
  have happened without the crash. A WAL alone is insufficient if replay loses
  recency -> append a touch record on every get hit (or store access timestamps).

  Append-only log specifics: a single write must not scale with cache size
  (so no dumping the whole dict per access). Append one {key, value} record on
  every access (hit and miss). On recovery, replay in order; each key's last
  occurrence fixes its LRU->MRU position and its value is the last written.

  Three corners that fail candidates:
    1. On replay you MUST call move_to_end for an already-seen key; reassigning
       an existing OrderedDict key does NOT change its order -> silently FIFO.
    2. Tuple cache keys must be converted to list before JSON serialization and
       back to tuple() on read.
    3. The final log line may be truncated by a crash mid-write and must be
       tolerated (skip the malformed tail).
  Bonus: log compaction (periodic snapshot + truncate); the hit path can append
  the key alone since the value is already known (saves I/O).
  One reported skeleton builds the key as
    (func_name, json.dumps(args), json.dumps(kwargs, sort_keys=True))
  where func_name is guaranteed unique; sort_keys is the part candidates miss.
