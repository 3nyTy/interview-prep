Tree Node Deletion → Max Height

Given an N-ary tree and a set of deleted nodes, compute the maximum height after deletion, with descendants promoted past deleted ancestors. The canonical follow-up asks for the minimum deletions needed to keep height at most `k`; one phone-screen variant explicitly disallows dynamic programming.

SWE
tree
dfs
recursion
dp
medium
Frequency
Medium
Last asked
2026-08-17
Stage
phone-screen · onsite-coding
Requirements
Base: tree given as edges or parent-pointer list (N-ary, not necessarily binary). A deleted set marks invalid nodes.
Deleted nodes are skipped in any height computation; their children effectively rise to attach at the nearest non-deleted ancestor.
Base output: the maximum root-to-leaf height after deletion.
Follow-up 1: given an integer k, return the minimum number of nodes to delete so that the post-deletion height is ≤ k.
Follow-up 2: on top of (1), among all min-deletion solutions, choose the one that maximizes the sum of depths of deleted nodes (prefer deleting deeper).
Own test cases expected; interviewers typically do not give one.
Examples
        1
       / \
      2   3
     /|   |
    4 5   6
        \
         7

deleted = {2}
# After deletion, 4 and 5 attach to 1.
# Heights: 1→4 (1), 1→5 (1), 1→3→6→7 (3)  → max = 3

Notes
Base case is one DFS: height(node) = 0 if node is deleted (treat as height 0 from its parent's perspective — the parent's other children still contribute); otherwise 1 + max(height(child) for child in children) with a tweak for deleted children.
The clean formulation: define effective_height(node) recursively where deleted nodes pass through their max-child height without adding 1.
Min-deletion-for-height-≤-k is a greedy / DP on the tree:
Greedy reading: process nodes by depth descending; whenever a node's subtree height exceeds k, delete the node and its excess subtree contribution collapses.
DP reading: at each node compute (min_deletions_to_make_subtree_height_≤_k, resulting_height) and roll up. The recurrence considers two cases per node: delete it (its children's subtrees become independent rooted at the parent of the deleted node) or keep it (subtree height = 1 + max(child heights), all child subtrees must individually satisfy the constraint).
The greedy version is faster to write but easier to get wrong on the "children rise to parent" semantics; the DP version is the safer choice in a screen.
The "prefer deleting deeper" follow-up is solved by adding a depth-weighted tiebreaker on the DP, breaking ties in favor of deeper deletions.
Edge cases: empty tree, root deleted (forest result), all leaves deleted, k = 0 (delete everything except root), k ≥ original height (zero deletions).
Interviewer constraint — no dynamic programming
A phone-screen variant explicitly disallows dynamic programming for the minimum-deletion follow-up. Clarify the restriction before committing to a recurrence, and keep a non-DP strategy ready.
Leave time to run tests: the constraint may not be stated until after the initial approach is discussed.
Preparation
Implement the base "skip deleted, return max height" DFS, then re-implement using iterative DFS with an explicit stack.
Implement the min_deletions(k) DP, then separately derive the depth-descending greedy path for the no-DP variant; use brute-force enumeration on a 6-7 node tree as the oracle before trusting the greedy invariant.
Drill the canonical pair of follow-ups together — they show up as a back-to-back ask in roughly half of recent Snowflake loops.
Binary-tree deletion variants
The binary-tree version uses unique node IDs and measures height as number of levels; if every node is deleted, return 0. Deleting a node promotes its children to the nearest non-deleted ancestor, and consecutive deleted nodes keep promoting descendants upward.
The min-deletions follow-up may be constrained to small trees (n <= 15). Under that bound, brute-force over deletion subsets is acceptable as a correctness oracle, while the DP / greedy tree solution remains the scalable answer.
Example: root = [1,2,3], targetHeight = 1 returns 1 because deleting node 1 leaves 2 and 3 as separate one-level roots.
